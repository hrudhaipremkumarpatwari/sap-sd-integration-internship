# Assumptions and glossary

## Working case assumptions

These are placeholders for a coherent learning case. Confirm or revise them in Week 1 and carry changes through all weeks. Do not present them as facts about an internship host.

| ID | Working assumption | How to use it |
|---|---|---|
| A-01 | A fictional mid-sized distributor is the case organization. | Give it a clearly fictional name or refer to it as “the case organization.” |
| A-02 | SAP SD is the order-to-cash process context. | Explain the relevant process scope; do not imply access to SAP. |
| A-03 | One external channel or business system exchanges order and status information with the SAP SD context. | Select and justify the external endpoint in the blueprint. |
| A-04 | Master data and transactional data require validation and traceability. | Define illustrative checks and ownership. |
| A-05 | Budget, work hours, volumes, service targets, and outcome metrics have no supplied real baseline. | Mark any values as estimates or simulated values and state the basis. |
| A-06 | The technical design is logical and vendor-neutral where possible. | Name products or protocols only as proposals, with rationale and alternatives. |
| A-07 | No real end users were interviewed for this scaffold. | Any feedback used in Week 4 must be described as hypothetical/synthesized. |

## Evidence labels

- **Source fact:** supported by a cited public source or the supplied internship brief.
- **Assumption:** an input chosen to make the case study workable; include an ID where useful.
- **Recommendation / proposed:** a design or action suggested by the report, not implemented.
- **Estimate:** a forecast such as effort, budget, or schedule, with a stated estimation basis.
- **Illustrative:** an example value or scenario used to explain an approach.
- **Simulated:** a modeled result that is not an observed production or test outcome.
- **Observed:** reserve for activity or evidence actually performed/collected; describe its source and date.

## Glossary

| Term | Working definition |
|---|---|
| SAP SD | SAP Sales and Distribution, the sales process area used as the case-study context. |
| Order-to-cash (O2C) | Business process from customer order through delivery, billing, and settlement. Exact boundaries vary by organization. |
| Integration point | A business or technical boundary where systems exchange or synchronize information. |
| Interface | The defined contract and mechanism used to exchange data between systems. |
| Middleware | A component or service that mediates, routes, transforms, or monitors exchanges between systems. |
| Idempotency | A property that makes repeated processing of the same request safe from unintended duplicate effects. |
| Reconciliation | Comparing records or totals across systems to identify missing, duplicate, or inconsistent exchanges. |
| DLQ | Dead-letter queue; a holding area for messages that cannot be processed automatically and need controlled review. |

Expand the glossary only when a term is used in the deliverables. Verify product-specific definitions against current public documentation and cite it.
